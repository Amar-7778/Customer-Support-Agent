### 1. Why Docker was Introduced

Docker was included because the initial specification stated:
> *"STACK: Python, LangGraph, ChromaDB, FastAPI, SQLite (queues, feedback, logs), Groq, sentence-transformers, Docker, React frontend, Git."*

In modern AI agent deployments, Docker serves a specific purpose for the **Python backend**:
- **Native C++ & PyTorch Dependencies:** ChromaDB uses native C++ vector libraries (HNSWLib), and `sentence-transformers` depends on PyTorch. Docker guarantees these compile and run identically on any Linux server, Windows, or macOS without local environment discrepancies.
- **Persistent Disk State:** The vector store (`chroma_db/`) and ticket queues (`support_system.db`) rely on persistent local disk writes.

#### Why the Backend Cannot Run Purely on Vercel Serverless:
1. **Serverless Filesystem is Ephemeral:** Vercel functions have a read-only filesystem with a temporary `/tmp` that gets wiped between cold starts. ChromaDB and SQLite would lose their indices and ticket state on function restarts.
2. **Bundle Size Limit:** Vercel Serverless functions have a 250MB uncompressed limit. PyTorch + `sentence-transformers` exceeds this size.

#### Best Practice with Vercel:
- **Frontend on Vercel:** We deploy the `frontend/` directory directly to Vercel (or via Git integration). It gives you instant preview URLs, edge caching, and global performance.
- **Backend:** Runs as a standard FastAPI service (either locally via `uvicorn src.api:app --port 8000`, or containerized on Railway/Render/Fly.io if you want it live in the cloud).
- **If you do not want Docker at all:** We do not need to use it! You can run the backend with standard `python` / `uvicorn`, and deploy the frontend to Vercel with zero Docker dependencies.

## 1. System Architecture & Workflow

The platform implements an autonomous, safety-gated support triage pipeline orchestrated via [LangGraph](file:///d:/Novintix/src/agent.py):

```mermaid
flowchart TD
    A[Customer Query] --> B[Intent & Urgency Classifier (Groq / GPT-OSS-20b)]
    B --> C{Human-in-the-Loop Check}
    C -->|High Urgency / High Risk / Negative Sentiment| D[Human Escalation Queue (Sorted by Urgency: Critical first)]
    C -->|Autonomous Candidate| E[ChromaDB Vector Search (384-d, +0.05 Human Boost)]
    E --> F{Similarity Score}
    F -->|Score >= 0.80| G[Found Solved Case: Use Human Resolution Grounding]
    F -->|0.55 <= Score < 0.80| H[Related Scenarios: Synthesize Grounded Solution]
    F -->|Score < 0.55| D
    G --> I[Synthesize Reply & Request Feedback]
    H --> I
    I --> J{Customer Feedback}
    J -->|Okay (Positive)| K[Persist & Index into ChromaDB as Validated Case]
    J -->|Not Okay (Negative)| L[Developer Review Flag & Failure Analysis Trace]
```

### Core Components Built
1. **Classifier Interface ([`src/classifier.py`](file:///d:/Novintix/src/classifier.py)):**
   - Implements abstract `BaseClassifier` and production `GroqClassifier`.

# Novintix: Product Requirements Document (PRD)

## 1. Executive Summary & Problem Framing

### The Operational Problem
Enterprise customer support teams process high volumes of inbound tickets across fragmented hardware, software, and billing verticals. Identifying the critical 15% to 25% of inquiries requiring immediate human specialist intervention is difficult:
- **Catastrophic Failure Modes:** Naive generative agents attempt to automate everything, leading to hallucinations on data loss, security lockouts, or financial disputes.
- **Queue Congestion:** Overly conservative keyword routing floods specialist queues with routine questions, causing SLA breaches on genuine emergencies.

### The Novintix Approach
Novintix implements an **asymmetric, safety-first, stateful intelligence platform** orchestrated via a **LangGraph state machine**. Rather than treating customer support as single-turn text generation, Novintix decouples the pipeline into six distinct operational phases:
```
[Raw Ingestion] -> [Multi-Attribute Triage] -> [HITL Escalation Gate] -> [ChromaDB Vector Retrieval] -> [Calibrated Synthesis] -> [Closed-Loop Feedback]
```

---

## 2. Core Features & System Capabilities

| Feature Module | Technical Implementation | Operational Role |
| :--- | :--- | :--- |
| **Multi-Attribute Groq Classifier** | Single-pass structured JSON inference (`llama-3.3-70b-versatile` / `llama-3.1-8b-instant`). | Simultaneously extracts intent, confidence ($0.0 - 1.0$), sentiment, urgency (`low`, `medium`, `high`, `critical`), and urgency rationale in $< 350\text{ms}$. |
| **Dynamic HITL Escalation Gate** | Deterministic policy evaluation engine embedded in the LangGraph state machine (`_hitl_check_node`). | Intercepts high-risk intents, critical urgencies, low confidence ($< 0.60$), and repeated customer contacts before automated generation. |
| **Priority-Sorted Human Queue** | Persistent SQLite transactional store (`src/database.py`). | Organizes escalated tickets into a specialist queue strictly ordered by urgency level (`critical` first, then `high`), ensuring zero SLA breaches on emergencies. |
| **Rank-Boosted Vector Retrieval** | Embedded ChromaDB persistent vector store (`data/chroma_db/`) containing 2,743 verified historical resolutions. | Executes cosine similarity search on 384-d dense embeddings (`all-MiniLM-L6-v2`) with a $+0.05$ score boost for human-authored resolutions. |
| **Three-Tier Calibrated Response Engine** | Conditional similarity branching node (`_decide_similarity_node`). | Differentiates between exact historical matches ($\ge 0.80$), related scenario synthesis ($0.55 - 0.80$), and ungrounded fallbacks ($< 0.55 \implies \text{Escalate}$). |
| **Closed-Loop Feedback Telemetry** | Dual-channel feedback endpoint (`/api/tickets/{id}/feedback`). | Positive ratings index verified solutions into vector memory; negative ratings dispatch complete execution traces to a developer review interface. |
| **High-Density Operator Console** | Responsive React 19 + Vite frontend application (`frontend/src/App.jsx`). | Zero-emoji, zero-gradient, high-information-density operations console providing real-time telemetry, node execution receipts, and queue management. |

## 3. Triage Workflow (State Machine Execution Graph)

```mermaid
flowchart TD
    User([Customer Ticket Ingestion]) --> NodeClassify[Node 1: Multi-Attribute Groq Classifier\nExtract: Intent, Confidence, Urgency, Sentiment]
    
    NodeClassify --> NodeHITL{Node 2: HITL Escalation Gate\n- High-Risk Intent?\n- Urgency: High/Critical?\n- Sentiment: Strongly Negative?\n- Confidence < 0.60?}
    
    NodeHITL -- "Yes (Escalate)" --> ActionEscalate[Node 3: Escalate to Human Specialist\nPersist to SQLite Queue: Urgency Ordered]
    ActionEscalate --> EndEscalate([Human Review Workflow])
    
    NodeHITL -- "No (Safe)" --> NodeSearch[Node 4: ChromaDB Precedent Search\nQuery Top-3 Cases filtered by Intent]
    
    NodeSearch --> NodeSimTier{Node 5: Similarity Scoring\nBoost: human_resolved +0.05}
    
    NodeSimTier -- "Score >= 0.80 (FOUND)" --> NodeAdapt[Node 6A: Direct Precedent Adaptation\nGround on matching historical human fix]
    NodeSimTier -- "0.55 <= Score < 0.80 (RELATED)" --> NodeSynthesize[Node 6B: Grounded Scenario Synthesis\nDraft response strictly bounded by related cases]
    NodeSimTier -- "Score < 0.55 (LOW)" --> ActionEscalate
    
    NodeAdapt --> NodeDeliver[Node 7: Customer Delivery & Response Ledger]
    NodeSynthesize --> NodeDeliver
    
    NodeDeliver --> NodeFeedback{Node 8: Customer Feedback}
    NodeFeedback -- "Positive (Okay)" --> ActionLearn[Add to ChromaDB as agent_generated_approved]
    NodeFeedback -- "Negative (Not Okay)" --> ActionDevAlert[Log Full Node Trace to Developer Review Queue]
```

### Execution Steps:
1. **Intake & Normalization:** Query text, metadata, and optional ticket IDs are normalized into `AgentState`.
2. **Intent & Urgency Classification:** Groq LLM extracts multi-attribute schema with explicit urgency reasoning.
3. **Safety Policy Evaluation:** Evaluates deterministic business rules. If any safety boundary is crossed, execution short-circuits immediately to human escalation without generating an automated reply.
4. **Precedent Retrieval:** For safe inquiries, ChromaDB retrieves the top-3 nearest semantic precedents within the predicted intent bucket.
5. **Similarity Tier Evaluation:** The agent computes the maximum boosted cosine similarity score across retrieved hits:
   - **Tier 1 ($\ge 0.80$ - FOUND):** Direct adaptation of verified historical human resolution.
   - **Tier 2 ($0.55 - 0.80$ - RELATED):** Grounded multi-scenario synthesis strictly constrained by retrieved precedents.
   - **Tier 3 ($< 0.55$ - LOW):** Knowledge gap detected; automatically diverts to the human queue.
6. **Customer Delivery & Trace Logging:** The response is returned to the customer, and the full state trace (latencies, similarity scores, prompt outputs) is committed to SQLite.
7. **Feedback & Memory Update:** Positive feedback triggers dynamic vector indexing. Negative feedback triggers an immediate developer incident alert.

## 4. Dataset Choice & Empirical Data Quality Audit

### 4.1 Selection of the Kaggle Customer Support Corpus
We selected the comprehensive Kaggle Customer Support Ticket Dataset (`customer_support_tickets.csv`, 8,469 raw records) covering five major hardware and software product verticals (Electronics, Laptops, Mobile Devices, Smart Home/Peripherals, and Productivity Software).

```
Total Tabular Rows:           8,469
Cleaned & Validated Rows:     8,398 (71 corrupted / empty rows purged)
Resolved Tickets with Text:   2,769
Deduplicated Solved Vectors:  2,743 (Indexed into ChromaDB with zero synthetic padding)
```

### 4.2 Three Critical Audit Discoveries
1. **Synthetic Priority Label Inversion:**
   The raw dataset featured a perfectly uniform priority distribution (~25% per tier). In **42 out of 75 golden evaluation cases**, the synthetic priority directly inverted real-world urgency:
   - Ticket #118: Google Nest crash with complete data loss was labeled `Medium`.
   - Ticket #123: Dell XPS app bug causing data loss was labeled `Low`.
   - Ticket #136: Samsung Galaxy document disappearance was labeled `Low`.
   *Architectural Decision:* Discarded the raw `Ticket Priority` column as ground truth and instituted an LLM-powered semantic urgency classifier that evaluates severity directly from customer descriptions.
2. **Resolution String Quality Divergence:**
   Many raw resolution fields contained synthetic Faker sentences (e.g. *"Case maybe show recently my computer follow"*).
   *Architectural Decision:* Used retrieved resolutions as structured diagnostic anchors rather than verbatim templates, requiring strict factual grounding.
3. **High Routine Concentration:**
   Over 45% of inquiries focused on repetitive, non-urgent setup issues (e.g. Bluetooth pairing, Wi-Fi reconnection), representing high-confidence candidates for automated resolution.

## 6. Escalation & Urgency Rules Engine

The HITL gate enforces five deterministic escalation rules:

```
IF (Rule 1: High-Risk Intent) OR
   (Rule 2: Critical / High Urgency) OR
   (Rule 3: Negative Sentiment / Repeat Contact) OR
   (Rule 4: Classifier Confidence < 0.60) OR
   (Rule 5: Precedent Similarity < 0.55)
THEN ESCALATE_TO_HUMAN
ELSE PROCEED_TO_AUTOMATED_RESOLUTION
```

1. **Rule 1 (High-Risk Intent Gating):** Financial transactions, legal compliance, PII management, and data recovery carry high operational liability and cannot be delegated to autonomous generative agents.
2. **Rule 2 (Semantic Urgency Override):** Inquiries classified as `urgency = "critical"` or `urgency = "high"` escalate immediately regardless of intent (e.g. total data loss or device overheating).
3. **Rule 3 (Customer Frustration & Repeat Contact Velocity):** Strongly negative sentiment or repeat contact indicators (`"multiple times"`, `"again"`, `"unresolved"`) trigger immediate human escalation.
4. **Rule 4 (Classifier Confidence Threshold):** If the intent classifier returns `confidence < 0.60`, the ticket escalates to prevent improper routing.
5. **Rule 5 (Precedent Retrieval Similarity Floor):** If the top retrieved ChromaDB precedent exhibits `boosted_similarity < 0.55`, the agent refuses to guess and routes the ticket to the human queue.

## 7. Calibrated Threshold Decisions

| Hyperparameter | Value | Mathematical Definition | Empirical Rationale |
| :--- | :--- | :--- | :--- |
| **Confidence Escalation Floor ($\tau$)** | `0.60` | $\text{Confidence} < 0.60 \implies \text{Escalate}$ | $\tau = 0.50$ allowed 21.4% false auto-handling on ambiguous queries, while $\tau = 0.70$ caused unnecessary escalation on 52.0% of routine queries. $\tau = 0.60$ achieved optimal Escalation F1 (0.7778). |
| **Precedent Similarity High ($\sigma_{\text{high}}$)** | `0.80` | $\text{Score} \ge 0.80 \implies \text{Direct Adapt}$ | Cosine similarity $\ge 0.80$ represents near-identical symptom descriptions where 100% of audited cases shared the exact same root cause. |
| **Precedent Similarity Medium ($\sigma_{\text{med}}$)** | `0.55` | $0.55 \le \text{Score} < 0.80 \implies \text{Scenario Synthesis}$ | Captures related failure modes within the same device family, providing sufficient context for grounded multi-scenario synthesis. |
| **Precedent Similarity Low ($\sigma_{\text{low}}$)** | `< 0.55` | $\text{Score} < 0.55 \implies \text{Escalate}$ | Below 0.55, precedents diverge into unrelated product categories, generating a 65% hallucination rate during testing. |
| **Human Precedent Rank Boost** | `+0.05` | $\text{Score}_{\text{boosted}} = \min(1.0, \text{Score}_{\text{raw}} + 0.05)$ | Prioritizes battle-tested human resolutions over agent-generated drafts in cosine space. |
| **Embedding Dimension & Model** | `384` (`all-MiniLM-L6-v2`) | $\vec{v} \in \mathbb{R}^{384}$ | Provides sub-15ms local inference per query on standard CPU, eliminating vector embedding latency bottlenecks. |

## 8. The Core Trade-off: Missed Urgent Tickets vs. False Alarms

### The Asymmetric Risk Formulation
In enterprise customer support, the cost of errors is asymmetric:
$$\text{Cost}(\text{False Auto-Handle}) \gg \text{Cost}(\text{False Escalation})$$

- **False Negative (Missed Urgent Ticket):** Auto-handling an unrecoverable data loss incident or disputed credit card charge leads to customer churn, brand damage, and legal liability ($C_{\text{fn}} \approx 5 \times C_{\text{fp}}$).
- **False Positive (False Alarm):** Routing a routine Wi-Fi pairing query to a human specialist incurs minor labor overhead but zero liability or customer churn.

### The 5:1 Cost-Asymmetric Optimization
$$\text{Loss}_{\text{total}} = 5 \times \text{Rate}(\text{False Auto-Handle}) + 1 \times \text{Rate}(\text{False Escalation})$$

### Empirical Results on 75 Golden Holdouts

| Metric / Risk Level | Trivial Baseline *(Always Escalate)* | Simple Baseline *(Keyword / Naive Conf)* | Novintix Agent *(Calibrated LangGraph Policy)* |
| :--- | :--- | :--- | :--- |
| **Intent Accuracy** | 18.67% | 44.00% | **60.00%** |
| **Urgent Detection F1** | 0.0000 | 0.4138 | **0.6557** (Prec: 0.80, Rec: 0.56) |
| **Escalation F1 Score** | 0.6383 | 0.5217 | **0.7778** |
| **False Auto-Handle Rate** *(Safety Hazard)* | 0.00% | 45.45% | **12.12%** *(73% relative risk reduction)* |
| **False Escalation Rate** *(Labor Overhead)* | 100.00% | **4.76%** | 35.71% *(Deliberate safety buffer)* |
| **Autonomous Throughput Rate** | 0.00% | **68.00%** | 44.00% |
| **Asymmetric Risk Score (5:1 Penalty)** | 0.8000 | 0.6133 | **0.4533** *(Lowest expected operational cost)* |

### Strategic Operating Point
The Simple Baseline achieves 68.0% autonomous throughput, but incurs a catastrophic **45.45% false auto-handle rate on critical tickets**. 

Novintix operates at a **44.0% autonomous handling rate** with a **12.12% false auto-handle rate**. By accepting a 35.71% false escalation rate on borderline cases, Novintix ensures human inspection on ambiguous tickets and achieves the lowest overall operational liability score (**0.4533**).
